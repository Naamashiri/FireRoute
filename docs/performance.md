# בדיקות ביצועים של FireRoute

בדיקות הביצועים מודדות אם השירות נשאר מהיר ותקין כאשר משתמשים רבים בודקים התרעה ומבקשים מסלול חירום בו־זמנית. הן אינן שולחות עומס לפיקוד העורף: השרת חייב לרוץ עם מקור ההתראות המדומה.

## מה נמדד

| מדד | משמעות |
|---|---|
| Throughput | מספר בקשות שהשרת מסיים בשנייה |
| p50 | זמן התגובה של המשתמש האמצעי |
| p95 | 95% מהבקשות הסתיימו עד זמן זה |
| p99 | זמן התגובה של מקרי הקצה האיטיים |
| Error rate | בקשות HTTP שנכשלו או תשובות שאינן תקינות עסקית |
| Concurrent VUs | מספר המשתמשים המדומים שפועלים במקביל |

`application_errors` הוא מדד משלנו: הוא נכשל גם כאשר התקבל HTTP 200 אבל גוף התשובה אינו חוזה FireRoute תקין.

## הכנה

1. מתקינים [k6](https://grafana.com/docs/k6/latest/set-up/install-k6/).
2. בונים ומריצים את ה־JAR במצב simulated:

```bash
cd fireRoute
mvn clean package
java -jar target/FireRoute-1.0-SNAPSHOT.jar --fireroute.alerts.source=simulated
```

3. בטרמינל נוסף, משורש הריפו, מריצים את אחת הבדיקות.

## Smoke קצר

```bash
k6 run -e K6_SMOKE=true performance/load-test.js
```

משתמש יחיד למשך עשר שניות. הבדיקה מיועדת לוודא שהתסריט והשרת עובדים, והיא רצה גם ב־CI. זו אינה מדידת capacity.

## עומס מדורג

```bash
k6 run performance/load-test.js
```

התסריט עולה מ־10 ל־50 ול־100 משתמשים. כל משתמש בודק מצב התרעה, מאתר צומת ומבקש מסלול חירום, ואז ממתין שנייה כמו לקוח אמיתי.

יעדי ברירת המחדל:

- פחות מ־1% שגיאות HTTP.
- פחות מ־1% תשובות שגויות עסקית.
- p95 כללי מתחת ל־500ms.
- p95 למסלול חירום מתחת ל־750ms.

## קפיצה המדמה אזעקה

```bash
k6 run performance/alert-spike-test.js
```

התסריט מפעיל התרעה מדומה, קופץ בתוך עשר שניות מ־10 ל־200 משתמשים, מחזיק את השיא דקה ואז מוריד עומס. בסיום הוא מכבה את ההתרעה המדומה.

יעדי ברירת המחדל מעט רחבים יותר בגלל העלייה החדה: p95 כללי מתחת לשנייה ו־p95 למסלול חירום מתחת ל־1.5 שניות.

לשרת שרץ בכתובת אחרת:

```bash
k6 run -e BASE_URL=http://server:8080 performance/load-test.js
```

## איך לבצע מדידה אמינה

- מריצים את ה־JAR ולא את השרת מתוך IDE.
- מבצעים warm-up לפני תוצאה רשמית.
- מריצים לפחות שלוש פעמים ומדווחים חציון.
- מתעדים מעבד, זיכרון, מערכת הפעלה וגרסת Java.
- למדידת production מריצים את k6 ממחשב אחר, כדי שהמחולל והשרת לא יתחרו על אותו CPU.
- עוקבים במקביל אחרי CPU, זיכרון ו־GC. תסריטי k6 מודדים את חוויית הלקוח, לא את סיבת ההאטה בתוך השרת.
- אין להסיק מבדיקת laptop כמה משתמשים יחזיק שרת production שונה.

## תבנית תוצאה לריאיון

```text
תאריך:
גרסת commit:
סביבת שרת: CPU / RAM / OS / Java
סביבת k6:
תרחיש ומספר משתמשים:
משך:
בקשות לשנייה:
p50 / p95 / p99:
אחוז שגיאות HTTP:
אחוז application_errors:
שיא CPU וזיכרון:
מסקנה וצוואר הבקבוק הבא:
```

אין למלא מספרים משוערים. טענה מקצועית על capacity חייבת להגיע מהרצה מתועדת בסביבה מוגדרת.
